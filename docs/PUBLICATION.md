# Publication boundary

The initial portfolio release uses a reviewed clean snapshot in a fresh repository with fresh history. Subsequent releases update that public repository with ordinary commits; never reset its history just to release a new version. Keep the existing development repository private; do not change its visibility or mirror archived refs. One maintained implementation feeds both releases, with an explicit source manifest for each promotion.

Public source is synthetic only. Preserve the current `UNLICENSED` position: publicly readable source grants no reuse rights. Bundled font licenses and notices remain in force. The owner-provided YourSet mark is included for this product; no production application code is copied.

Before pushing the exact release, record its source commit, included-file manifest, asset provenance, dependency/advisory report, synthetic browser results and history audit. Verify a clean install/build and a complete decision/review walkthrough. Documentation must distinguish local synthetic validation from source integration and operational use. See the [capability matrix](CAPABILITIES.md).

The static build uses an explicit file allowlist. It excludes collectors, provider projections, SQL, private configuration and validation records. No private API, credentials or real-data imports belong in that bundle. The approved synthetic demo uses the existing Vercel project linked to the public repository. `vercel.json` selects the Other framework preset, runs JavaScript tests followed by the allowlisted build, and sets `dist/` as the only output directory. No private API or database is deployed. One function runs outside `dist/`: `api/cron/engine-canary.js`, which Vercel Cron calls daily (the `crons` entry in `vercel.json`). It recomputes the bundled synthetic scenarios through the shared metric engine on the production Node runtime and compares a digest with the one CI pins, returning 503 on any difference. It reads no other data and accepts only `Authorization: Bearer $CRON_SECRET`. Complete the full local and public CI checks before accepting a release; Vercel Git deployments run independently of GitHub Actions. Hosting changes beyond this static destination and that canary remain separate decisions.

Review secrets **and ordinary personal measurements**. A secret scanner cannot establish that a table or screenshot is synthetic. Private planning, real records, operational reports and credentials stay outside the source tree. Never copy private preview fixtures, screenshots or repository history into the public release. Public copies cannot be recalled by reverting visibility.

## Reproducible source export

`docs/release-files.txt` is the exact source allowlist, reviewed before each release. From a committed candidate, run `node scripts/export-source.mjs EMPTY_DESTINATION HEAD`. It reads Git blobs from that commit, preserves executable modes, refuses a nonempty destination and emits `SOURCE_RELEASE.json` with content hashes. It copies no `.git` directory or archived refs. For the first release, initialize fresh history in the destination. For updates, compare the export to the clean public checkout and copy only the manifest-listed files and `SOURCE_RELEASE.json`; explicitly review removed files. Preserve its `.git` directory and existing public commits. Run the documented clean-install, build, browser, privacy and dependency checks against the exact public candidate before pushing. Keep the private source/public release mapping in an external release ledger.

The manifest identifies the private source commit and hashes the exported files. It establishes file provenance, not public access to that private commit or proof that a historical test was run. CI attaches new evidence to public commits. Keep earlier local measurements dated and labelled as local observations.

## Hosted demo verification

The site is [YourSet Insights](https://yourset-insights-demo.vercel.app/). Vercel deploys commits from the public repository's `main` branch. The [checks workflow](https://github.com/pkkeable/yourset-insights-demo/actions/workflows/privacy.yml) separately verifies the built artifact in Chromium under `/yourset-insights-demo/`, so the build works under both an origin root and a project subdirectory. Do not point the host at the private repository or set `server.mjs` as the deployment entry point.

After deployment, run `npm run test:demo -- --url https://yourset-insights-demo.vercel.app/` from the reviewed checkout. Check the exact deployed asset hashes against the local build as well. Hosted synthetic behavior does not establish a private installation or live-source operation.

The built HTML carries a content security policy that disallows application network connections. The app bundles its fonts and makes no analytics or provider calls. The hosting provider still handles normal web-server requests; see [Vercel's privacy policy](https://vercel.com/legal/privacy-policy).

The initial automatic deployment treated the local `server.mjs` as a function and failed at invocation because it has no default function/server export. The explicit static configuration avoids that runtime entirely. The static demo requires no environment secrets or database. Only the canary reads `CRON_SECRET`, a sensitive Production variable set in Vercel and never stored in the repository; without it the canary refuses every request. [Vercel configuration reference](https://vercel.com/docs/project-configuration/vercel-json).
